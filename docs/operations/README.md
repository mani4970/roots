# Roots 상시 운영 진단 v3

기준: `roots_safe_current_20260928_1841.zip` / 2026-09-28.
이 문서는 배포 후 운영자가 기록을 해석하고 대응하는 방법입니다. 최초 적용 순서는 패치 ZIP의 `README_ko.md`에 있습니다.

## 수집 범위

| 구간 | 남는 근거 | 해석할 때의 경계 |
|---|---|---|
| 로그인·가입·비밀번호 재설정 | 요청, SDK 오류 코드, 재시도 횟수, 처리 결과, 안내 문구 키·DOM 표시 | 로그인 전 실패는 익명. 비밀번호 분실 여부·입력 이메일은 알 수 없음 |
| OAuth | 시작 요청, 시작 단계 실패, 리디렉션 시작 | 리디렉션 시작을 로그인 성공으로 판정하지 않음. 외부 제공자·콜백 전체 추적은 별도 로그 대조 필요 |
| QT 글쓰기 | 임시저장·본문·공유·진행도·완료 화면 단계, 같은 작업의 flow_id·record_id | 저장·공유·보상·화면 완료는 서로 다른 단계. 날짜·모드·계정이 바뀌면 작업을 분리 |
| QT 사진 | 기존 업로드·검증·기록·공유·완료 단계 | 사진 자체·경로·URL은 수집하지 않음 |
| 기도·나눔 | 기존 생성·수정·응답·공유·롤백·새로고침 단계 | 본문 존재만으로 공유·화면 갱신까지 성공했다고 판정하지 않음 |
| 홈·보상·팝업 | 기존 자격 확인·대기·DOM 표시·겹침·확인·닫힘 | DOM 표시와 실제 사람의 인지는 다름. 미표시가 모두 오류인 것은 아님 |
| 수집 상태 | app_ready, 5분 간격 전경 heartbeat, 전송 포기/초과 건수, 마지막 수신, 보관 정리 상태 | 기기 강제 종료·차단·네트워크 단절로 누락될 수 있음 |

`user_id`는 수신 서버에서 Supabase `getUser()`로 확인한 계정입니다. 익명 인증 시도는 `user_id=null`입니다. 임시 서명 쿠키의 `session_id`와 `flow_id`로 같은 브라우저의 재시도 흐름을 볼 수 있으며, 나중에 로그인한 계정은 `later_authenticated_user_id`에 별도 표시됩니다. 그 사람이 앞서 입력한 이메일의 소유자였다는 뜻은 아닙니다.

웹 배포 버전은 Git 커밋 SHA, 기기는 플랫폼 종류와 브라우저 주 버전으로 기록합니다. 네이티브 앱은 App 플러그인이 정보를 반환한 뒤부터 앱 버전·빌드 번호를 추가합니다. 단말 고유 식별자, 전체 User-Agent, 이메일·이름·비밀번호·토큰·묵상/기도 본문·사진·수신자 ID는 진단에 저장하지 않습니다.

고정 `build_tag=obs-20260916-v1`는 기존 이벤트 계약 호환 필드입니다. 이번 수집 경로의 버전은 `protocol=3`, 실제 실행 코드의 버전은 `details.release`입니다. Vercel 이외 빌드에서는 `ROOTS_RELEASE_SHA`에 실제 커밋 SHA를 지정할 수 있습니다. `local`/`unknown`은 배포 버전 미확인으로 보고합니다.

## 운영 조회

SQL Editor에서 `investigate.sql`을 실행합니다. 첫 결과는 수집 상태, 다음은 최근 오류와 회복 근거·현재 QT/기도 기록 상태, 이어서 기기/버전별 집계와 긴급 조사 후보입니다. 최근 오류 조회는 200건, 로컬 보고서는 2,000건까지이므로 필요하면 시간·user_id·flow_id로 범위를 좁힙니다.

로컬 서버 환경변수가 있는 프로젝트에서는 다음 읽기 전용 명령도 가능합니다.

```bash
node scripts/ops-report.mjs
```

`NEXT_PUBLIC_SUPABASE_URL`과 서버 전용 `SUPABASE_SECRET_KEY`를 사용합니다. 키를 브라우저 코드나 공개 저장소에 넣지 않습니다. 출력에는 운영용 UUID가 들어가므로 필요한 운영자 범위에서 확인합니다. 이 명령은 메시지 전송이나 DB 변경을 하지 않습니다.

특정 건의 상세 순서(아래 UUID는 조회할 flow_id로 바꿉니다):

```sql
select received_at, client_at, user_id, flow_id, scope, event_name,
       client_kind, record_id, details
from public.app_ops_events
where flow_id = '00000000-0000-4000-8000-000000000000'::uuid
order by client_at, received_at;
```

같은 계정과 같은 기록 ID로 다른 flow를 조회하면 페이지 재진입 후 저장도 대조할 수 있습니다. 연결할 record_id가 없는 과거/오프라인 실패를 임의로 다른 완료 건에 붙이지 않습니다. 계정 확인은 Supabase 사용자 목록에서 user_id로 조회합니다.

## 해결 여부를 판단하는 순서

1. 오류가 난 기능·단계와 기술 코드, 사용자/익명 여부, 배포·단말 버전을 확인합니다.
2. 같은 flow에서 이후 **같은 단계**가 성공했는지 봅니다. 비밀번호 재설정 접수는 로그인 실패 해결로 처리하지 않습니다. 공유 대상 저장 실패를 공개 범위 저장 성공으로 해결 처리하지 않습니다.
3. record_id와 user_id가 일치하는 실제 DB 기록을 대조합니다. 본문, 공유 대상, 진행도/보상은 각각 확인합니다.
4. 완료 화면 표시·확인 이벤트를 따로 확인합니다. DB 저장 성공만으로 화면 표시를 단정하지 않습니다.
5. 근거가 있으면 해당 단계의 회복을 기록합니다. 후속 기록이 없으면 **해결 근거 없음 / 추가 확인 필요**입니다. 영구 실패나 데이터 유실로 단정하지 않습니다.

`app_ops_cases.recovery_state`는 `client_reported_recovery` 또는 `no_recovery_evidence`입니다. 영구적인 사건 관리 테이블이 아니라 보관 중인 이벤트로 계산하는 읽기 전용 조회입니다. 수동 조치·담당자·고객 문의 이력은 기존 운영 기록에 남깁니다. `client_at`은 기기 시계이므로 수신 시각과 함께 확인합니다.

긴급 조사 후보 기본값은 최근 15분의 미회복 운영 오류에서 동일 기능/단계/코드로 확인된 계정 3명 이상입니다. 익명 계정은 사용자 수에 합산하지 않습니다. 1명이라도 저장 유실 문의가 있으면 직접 조사합니다. 이 기준은 `investigate.sql`과 보고서에서 계산하며, 즉시 푸시·이메일·Slack 발송 장치는 아닙니다.

기존 매일 19:00 Europe/Berlin 보고와 실시간 알림은 구분합니다. 이 패치 ZIP은 기존 예약을 변경하거나 새 알림 채널을 연결하지 않습니다. 배포·수집 확인 후 `daily-report-prompt.txt`를 기존 보고의 지침에 반영하면 새 진단과 기존 Supabase 로그/Advisor를 함께 조사할 수 있습니다. 즉시 알림은 수신 채널·주기·중복 억제 설정을 확정한 뒤 별도 연결합니다.

## 수집 제어·보관·부하

- `app_ops_settings.enabled`로 기본 수집을 계속 켜거나 끕니다. 초기 설치는 꺼짐입니다.
- `detail-7-days.sql`은 해시 번들 파일명/행/열 정보만 7일간 추가합니다. 기간이 지나도 기본 수집은 계속되고 상세 기간은 자동 연장되지 않습니다.
- `app_ops_events`는 수신 후 30일 보관, 매시간 17분 정리합니다. 정상 실행 시 정리 간격만큼 최대 약 1시간 차이가 납니다. 작업 중단 시 더 길어질 수 있으므로 `last_cleanup_at`과 cron 실행 결과를 확인합니다. 기존 `app_observation_*` 관측 자료는 이 정리 대상에 포함하지 않았습니다.
- 브라우저 큐는 120개/1시간/최대 3회 전송 시도입니다. 한 번에 최대 30개·28KiB를 전송하고 수신은 32KiB까지입니다. 전송 실패를 업무 함수에서 기다리지 않습니다.
- 인증된 계정 240개/분, 익명 세션 60개/분, 네트워크 버킷 2,400개/분, 전체 25,000개/UTC일의 서버 한도를 적용합니다. 재전송도 트래픽 한도에는 포함됩니다. 최대치를 넘으면 진단을 버리고 본래 기능은 계속합니다.
- IP 원문은 저장하지 않고, 일 단위로 바뀌는 HMAC 버킷을 속도 제한에만 사용합니다. 버킷은 2일 뒤 정리합니다. 프록시 헤더와 공유 네트워크 특성상 네트워크 버킷은 사람 수를 뜻하지 않습니다. 공격을 완전히 방지하는 장치는 아닙니다.
- 같은 event_id의 재전송은 기존 오류를 덮어쓰지 않습니다. DB의 원자적 한도로 동시 요청의 초과를 제한합니다.

## 중지와 되돌리기

수집만 즉시 중지하려면 `disable.sql`을 실행합니다. 서버는 다음 수신부터 거부하고 클라이언트 설정은 최대 약 1분 내 반영됩니다. 보관 정리는 계속합니다.

코드 복원은 패치 도구의 백업으로 수행합니다. 복원 코드를 다시 배포해야 운영 코드도 복원됩니다. 패치 도구는 SQL/배포/계정/기록을 변경하지 않습니다. 진단 테이블을 급히 삭제할 필요는 없고, 비활성화 상태에서 근거를 보관해 원인을 확인할 수 있습니다.
